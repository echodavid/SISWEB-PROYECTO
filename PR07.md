PR07. Sistema de reportes ciudadanos
Complejidad orientativa: Media-alta Problema: Reportes sobre servicios comunitarios no muestran seguimiento,
prioridad ni evidencia suficiente para comunicar su estado. Usuarios: Ciudadano simulado, operador y responsable de
atencion.
Alcance minimo
Reporte, categoria, ubicacion textual no precisa, evidencia ficticia, estado, prioridad y seguimiento.
Exclusiones: Denuncias reales, geolocalizacion exacta, emergencias y publicacion de datos personales.
Datos y evolucion tecnica
Dimension Propuesta inicial
Entidades PostgreSQL reporte, categoria, zona, evidencia, seguimiento y evento_contexto.
Web 1.0 Consulta y alta de reporte con JSP/Servlets.
Web 2.0 Bandeja y cambio de estado mediante JSF/PrimeFaces.
Web 3.0 API de reportes y dashboard Angular por categoria/estado.
Web 4.0 Evento ambiental simulado que complementa un reporte sin identificar personas.

Requerimientos no funcionales comunes
• RNF01. Reproducibilidad. El proyecto debe ejecutarse desde un entorno limpio mediante README, versiones,
variables y comandos sin pasos secretos.
• RNF02. Seguridad y privacidad. Debe usar datos sinteticos, validar entradas, externalizar credenciales y aplicar
autorizacion en las operaciones que cambian estado.
• RNF03. Accesibilidad. Las vistas deben usar etiquetas, navegacion por teclado, mensajes comprensibles y contraste
suficiente como base de WCAG 2.2.
• RNF04. Integridad de datos. PostgreSQL debe aplicar llaves, relaciones y restricciones; los errores de negocio no se
resuelven solo en la interfaz.
• RNF05. Trazabilidad. PRxx, alcance, cambios, commits, pruebas y contribuciones individuales deben permanecer
relacionados.
• RNF06. Despliegue acotado. La demostracion puede ser local o en contenedor autorizado; no requiere nube, servicios
de pago ni infraestructura institucional.
Limites cuantitativos del producto minimo
Elemento Limite esperado
Flujo principal Uno completo de inicio a resultado; los flujos secundarios son opcionales.
Roles Hasta tres roles funcionales; no se exige administracion avanzada de identidad.
Modelo de datos Entre cinco y siete entidades principales, salvo justificacion aprobada.
API Web 3.0 Salud, consulta y cambio del flujo principal, con estados 2xx y 4xx demostrables.
IoT Web 4.0 Una fuente o flujo simulado con dispositivo, instante, variable, unidad y valor.
Pruebas Al menos dos casos positivos, dos negativos y una prueba del recorrido principal.
Integraciones externas Ninguna obligatoria; todo servicio externo debe poder sustituirse por simulacion.
Riesgo, control y comprobacion
Riesgo principal: Difamacion o datos sensibles; usar casos ficticios, moderacion y minimizacion. Pruebas minimas:
Validar transiciones, evitar campos sensibles y comprobar filtros y prioridades.
Criterios de aceptacion
• CA01. Desde una base inicial con datos sinteticos se completa el flujo principal y se observa el cambio persistido.

• CA02. El caso invalido indicado en las pruebas se rechaza con mensaje comprensible y sin alterar datos
incorrectamente.
• CA03. La API devuelve JSON coherente, usa un estado 2xx en exito y un 4xx en entrada o regla invalida.
• CA04. Un evento IoT simulado identifica fuente, instante, variable, unidad y valor; queda visible o persistido y produce la
interpretacion prevista.
• CA05. Otra persona puede preparar, ejecutar, probar y limpiar el incremento mediante el README.
• CA06. El equipo demuestra autoria, contribucion individual, limitaciones y cambios de alcance autorizados.
